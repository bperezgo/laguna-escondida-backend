## Context

See proposal.md, Why. Current state:
- `SignupService.create` (`backend/internal/domain/service/signup_service.go`) stores the admin, whose password is `unusablePassword()` so they can never sign in on the box. It also stores a manager named "Caja" with username `BoxUsername(email)` and a random password that nobody sees.
- "Instalar caja" step 3 (`frontend/components/settings/InstallBoxPageClient.tsx`, `PasswordStep`) picks the **oldest** active manager without an email (`findBoxUser`) and calls `POST /api/admin/users/:id/generate-password`. That is the hidden "Caja" user even when the owner has created their own manager.
- Every user except API-key users syncs to the box (`FindChangedUsers`), and the box signs in by `username` only. Emails never sync.
- Usuarios already has a "Contraseña" action (`ResetPasswordModal` → `POST /api/admin/users/:id/reset-password`, `users:update`, organization-scoped through `findStaffUser` and the tenant DB). Only `ResetPasswordModal` and `UsersPageClient` use it.

## Goals / Non-Goals

**Goals:**
- The admin creates the box's users and picks their passwords. Nothing is hidden or generated by the cloud.
- The page says plainly which username to type on the box.

**Non-Goals:**
- Deleting the "Caja" users that existing organizations already have. The admin can deactivate or rename them.
- Stopping users whose password is unusable (Google admins) from syncing to the box. They cannot sign in there, which is harmless. The page explains it.
- Telling the admin whether the box has already received a user. That belongs to the separate "box waits for its first user" change.
- The create-user form's own in-form password generator, which shows the password to the admin as they set it.

## Decisions

### D1. Signup stops creating the "Caja" user

It confused the first real owner, and once the admin creates their own box user, it is redundant. Removing it also removes the only case where an account with a credential exists that nobody holds. `BoxUsername`, `boxUserName` and `boxUserFallback` are deleted with it.

*Alternative: keep "Caja" and only change step 3 to "Cambiar contraseña" for it.* Rejected. The owner would still meet a user they did not create, with a username derived from their email, alongside the manager they did create.

### D2. Remove `generate-password` rather than keep it unused

Its only caller is step 3. Reset-password covers every case, because the admin types the password and so already knows it. Removing it deletes the route, the handler, the service method, the DTO, the proxy route, the client, the tests and the docs. The route golden file loses one line, and a test asserts the route now answers `404`.

*Alternative: keep it for API clients (MCP).* The MCP server has no generate-password tool (`tools_users.go` wraps only reset-password), so nothing outside the UI uses it.

### D3. Step 3 lists every active user without an email

A user without an email can only ever sign in on the box (the cloud requires an email for admin, accountant, agent and courier), so "no email" is the right test, not "oldest manager". Each row shows the username, the name and the roles, plus "Cambiar contraseña". That button opens the existing `ResetPasswordModal` on the Instalar caja page itself, so the admin does not have to leave the page. The page reuses `usersApi.getAll()` and `usersApi.resetPassword()`.

`findBoxUser` becomes `boxUsers(users)`: active users without an email, sorted by username, each keeping its roles.

### D4. "Crear usuario de caja" deep-links into Usuarios

The link goes to `/users?nuevo=caja`. `UsersPageClient` reads it once on mount, opens the create form with the manager role preselected and the email empty, and removes the parameter from the URL. The page does not get a second user form: Usuarios keeps the single create flow and its validation.

### D5. The copy

The step is titled "3. Usuarios de la caja". Its text: "En la caja se inicia sesión con el **usuario** (no con el correo). Tu cuenta de Google no sirve para la caja: crea un usuario de caja y ponle la contraseña que quieras." After a password change: "Contraseña cambiada. La caja la recibe en su próxima sincronización (cerca de un minuto)."

### D6. "Cambiar contraseña" is also in the Editar dialog

The owner looked for the password under "Editar" and missed the "Contraseña" button beside it. In edit mode, `UserForm` shows a "Cambiar contraseña" button that closes the form and opens the same `ResetPasswordModal` for that user. There is still one password flow.

## Security

**Boundary: an organization admin → the passwords of their organization's box users.**
- *Lower-trust principal:* a signed-in cloud user of organization A, holding any role.
- *Input they control:* the target user id and the new password on `POST /api/admin/users/:id/reset-password`. They also control which users the page lists, but it reads only their own organization's users through `GET /api/admin/users`.
- *Intended control:* unchanged and reused. The route requires `users:update` (`routes_cloud.go`, `RequirePermission`), and `UserService.ResetPassword` → `findStaffUser` loads the user through the tenant-scoped repository, so another organization's user is `404`. API-key users are refused. The password is hashed with `user.HashPassword` and never returned.
- *Protected resource:* other organizations' users, and box sign-in for this organization.
- *If the control fails:* an admin could set another tenant's box password and sign in on that box as that user.
- *What this change removes:* the generate-password endpoint, which returned a plaintext credential in a response body, and the signup-created account whose password nobody held. Removing them shrinks the surface. The new page keeps the admin's typed password in component state only, never in storage or the URL, and clears it when the modal closes.
- *Attack classes considered* (WEB-PROTOCOL-AND-AUTH.md, DATA-ISOLATION-AND-LIFECYCLE.md, CLIENT-SIDE.md): IDOR across tenants on reset-password, a missing role check, secrets in client storage or URLs (the `?nuevo=caja` parameter carries no secret), and a removed route that still answers.

No needs-validation items: everything is enforced in the repo.

## Risks / Trade-offs

- [The owner signs in on the box with their email and fails] → the step's copy says to use the username, and the box's sign-in page change (separate) can show the same hint.
- [An organization created before this change still has "Caja" with an unknown password] → it is listed in step 3 with "Cambiar contraseña", so the owner can set it or deactivate it in Usuarios.
- [The owner looked for the password change under "Editar" and missed the separate "Contraseña" button] → the Editar dialog also offers "Cambiar contraseña" (D6). Reset-password itself works.
- [Box sign-in depends on the box receiving users] → it needs PR #88 (the box's organization row; without it every pull rolled back on `users_organization_id_fkey`). Merge #88 before this change's box sign-in scenario can pass end to end.

## Migration Plan

Depends on PR #88 for box sign-in end to end. No data migration. Deploy cloud and web together (`cloud/vX.Y.Z`). Rolling back restores the generator and the "Caja" creation. Organizations created in between simply have no "Caja" user. Boxes are unaffected.
